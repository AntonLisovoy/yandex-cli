# Настройка

Для Tracker/Wiki нужны токен и идентификатор организации. Календарю нужны
собственные OAuth-настройки и полный email; организация Tracker не требуется. На этой странице собраны все
способы это сообщить, места, где сказанное хранится, и то, как ограничить CLI
одним только чтением.

Если вам просто нужно начать работать, короткая версия есть в
[начале работы](getting-started.md).

## Откуда берутся настройки

Слоёв четыре. Каждый следующий перекрывает предыдущие — побеждает последний, у
кого есть мнение.

| № | Слой | Пример |
|---|---|---|
| 1 | Встроенные значения по умолчанию | `api_base_url=https://api.tracker.yandex.net`, `wiki_base_url=https://api.wiki.yandex.net`, `timeout=30.0` |
| 2 | Текущий профиль | `~/.yandex-cli/config.json` |
| 3 | Переменные окружения | `export TRACKER_TOKEN=y0_...` |
| 4 | Флаги командной строки | `yandex config check` |

То есть `TRACKER_ORG_ID`, экспортированный в оболочке, перебивает
идентификатор организации из профиля, а `--org-id` в командной строке
перебивает и то и другое.

> **Единственное исключение.** Явно переданный `--profile NAME` ставит этот
> профиль **выше** окружения для настроек. Credential-переменные полностью
> исключаются, даже когда у сервиса нет назначения в профиле.
> Запрос профиля по имени означает, что вам нужен именно он, а не то, что
> случайно экспортировано в этом окне. Без `--profile` текущий профиль остаётся
> на слое 2 и окружение побеждает.

Чтобы увидеть результат всех четырёх слоёв, спросите:

```bash
yandex config show
```

## Профили

Профиль — это именованный набор настроек, хранящийся в файле, чтобы набирать их
один раз, а не каждый раз. Это рекомендуемый способ хранить учётные данные: в
отличие от экспортированной переменной, которая живёт только в том окне
терминала, где вы её набрали, и в отличие от файла `.env`, который читается
только в том каталоге, где лежит, профиль работает из любого каталога в любом
окне, пока вы его не измените.

Профилей может быть несколько — по одному на организацию или отдельный профиль
только для чтения, чтобы отдать его скрипту, — и между ними можно переключаться
по имени.

### Создание и переключение

**Создать профиль.** `set-profile` создаёт его, если такого нет, и обновляет
названные вами поля, если он есть. `y0_exampletokenvalue` на этой странице
везде стоит вместо вашего собственного токена:

```bash
yandex config set-profile work --org-id 123456
yandex --profile work auth add main --services tracker,wiki --token-stdin < /secure/local/oauth-token
```

```
  profile: work
  config_file: /Users/you/.yandex-cli/config.json
  current: True
  saved: True
  ✓ Profile 'work' saved to /Users/you/.yandex-cli/config.json
```

Сохранение профиля заодно делает его текущим. Опция `--not-current` добавляет
профиль, не переключаясь на него:

```bash
yandex config set-profile cloud --cloud-org-id bpf1abc2def3ghi4jkl5 --not-current
yandex --profile cloud auth add main --services tracker,wiki --token-stdin < /secure/local/oauth-token
```

Кроме учётных данных `set-profile` принимает `--api-base-url`,
`--wiki-base-url`, `--limit-queues`, `--read-only` / `--no-read-only` и
`--wiki-read-only` / `--no-wiki-read-only`.

**Посмотреть список.** `CURRENT` отмечает используемый профиль; `TOKEN`
говорит лишь о том, сохранены ли учётные данные, но не о том, какие именно:

```bash
yandex config list-profiles
```

```
  Profiles
  ────────
  NAME  │ CURRENT │ ORG                  │ API │ TOKEN
  ────────────────────────────────────────────────────
  cloud │ no      │ bpf1abc2def3ghi4jkl5 │ -   │ set
  work  │ yes     │ 123456               │ -   │ set
  2 row(s)
```

**Переключиться.** Это действует до следующего переключения:

```bash
yandex config use-profile cloud
```

```
  profile: cloud
  current: True
  ✓ Active profile: cloud
```

**Использовать профиль для одной команды**, не переключаясь. `--profile`
ставится перед командой, потому что это настройка всей программы, а не одной
команды:

```bash
yandex --profile cloud tracker queue list
```

**Удалить профиль.** Если вы удаляете текущий профиль, текущим становится
другой — при условии, что он есть. Удалите последний профиль, и текущего не
останется, так что CLI перейдёт к окружению:

```bash
yandex config delete-profile cloud
```

```
  profile: cloud
  deleted: True
  ✓ Profile 'cloud' deleted
```

### Где хранятся профили

В `~/.yandex-cli/config.json`. Это файл JSON с ключом `current`, где назван
активный профиль, и объектом `profiles`, где лежит всё остальное:

```json
{
  "current": "work",
  "profiles": {
    "work": {
      "limit_queues": [],
      "org_id": "123456",
      "read_only_queues": [],
      "auth": {"version": 1, "tokens": {}, "services": {}}
    }
  }
}
```

**Токен хранится открытым текстом.** Ничто его не шифрует. Это тот же
компромисс, что и в файлах `~/.netrc` или `~/.aws/credentials`, и он означает,
что файл стоит беречь: ему не место в резервной копии, которой вы делитесь, в
синхронизируемой папке, доступной другим, или в git-репозитории. На машине, куда
могут заходить другие люди, ограничьте к нему доступ командой
`chmod 600 ~/.yandex-cli/config.json`.

Переменная `YANDEX_CLI_HOME` переносит весь каталог целиком — профили, сессию и
историю вместе — в другое место:

```bash
YANDEX_CLI_HOME=/secure/volume/yandex yandex config check
```

## Переменные окружения

Переменная окружения — это настройка, привязанная к запущенной программе, а не
к файлу. Она нужна тогда, когда файл на диске — неподходящее место для токена,
а такое бывает в основном там, где запускаете не вы, а что-то другое:

- **Конвейеры CI** — серверы, которые автоматически собирают и тестируют ваш
  код. Секреты каждому запуску они выдают из хранилища, и запись токена в файл
  там означала бы, что он попадёт в репозиторий, доступный всем.
- **Контейнеры** — заранее собранные одноразовые копии программы. Сборкой
  делятся со всеми; учётными данными делиться нельзя.
- **Разовая оболочка** — одно окно терминала, в котором вы хотите поработать от
  другого пользователя или с другой организацией, не трогая сохранённые
  профили.

Если ничего из этого к вам не относится, используйте профиль.

Задать переменную для одной команды можно, поставив её перед командой:

```bash
TRACKER_ORG_ID=654321 yandex tracker queue list
```

или на всё оставшееся время работы в окне терминала — с помощью `export`:

```bash
export TRACKER_TOKEN=y0_...
export TRACKER_ORG_ID=123456
yandex config check
```

Переменная, которой присвоена пустая строка, считается вообще не заданной,
поэтому `TRACKER_TOKEN=` не стирает токен в вашем профиле — значение из профиля
просто остаётся на месте.

### Полный список

| Переменная | Что делает |
|---|---|
| `TRACKER_TOKEN` | OAuth-токен. Нужны какие-то одни учётные данные из двух. |
| `TRACKER_IAM_TOKEN` | IAM-токен Yandex Cloud как альтернатива OAuth-токену. |
| `TRACKER_ORG_ID` | Идентификатор организации для Yandex 360 или локальной установки Tracker. |
| `TRACKER_CLOUD_ORG_ID` | Идентификатор организации в Yandex Cloud. Задавайте ровно один из двух. |
| `TRACKER_API_BASE_URL` | Адрес API Tracker. По умолчанию `https://api.tracker.yandex.net`. |
| `WIKI_API_BASE_URL` | Адрес API Wiki. По умолчанию `https://api.wiki.yandex.net`. |
| `TRACKER_READ_ONLY` | Логическое значение. Отклонять все команды Tracker, которые пишут. |
| `WIKI_READ_ONLY` | Логическое значение. Отклонять все команды Wiki, которые пишут. |
| `TRACKER_LIMIT_QUEUES` | Ключи очередей через запятую. Доступны будут только эти очереди. |
| `TRACKER_READ_ONLY_QUEUES` | Ключи очередей через запятую: их можно читать, но не изменять. |
| `TRACKER_TIMEOUT` | Сколько секунд ждать ответа API. По умолчанию `30.0`. |
| `YANDEX_CLI_HOME` | Каталог с настройками, сессией и историей. По умолчанию `~/.yandex-cli`. |
| `YANDEX_CLI_SESSION` | Путь к одному только файлу сессии; перекрывает путь внутри `YANDEX_CLI_HOME`. |
| `NO_COLOR` | Любое непустое значение выключает цветной вывод. |
| `YANDEX_CLI_NO_COLOR` | То же самое, но не затрагивая другие программы. |

Логические переменные принимают `1`, `true`, `yes` или `on` в любом регистре.
Всё остальное, включая `0` и `false`, означает «выключено». Исключение —
`NO_COLOR` и `YANDEX_CLI_NO_COLOR`: они проверяются лишь на то, заданы ли они
вообще, поэтому `NO_COLOR=0` тоже выключает цвет.

Ключи очередей сравниваются без учёта регистра:
`TRACKER_LIMIT_QUEUES="trek, ops"` и `TRACKER_LIMIT_QUEUES=TREK,OPS` означают
одно и то же.

Имена `TRACKER_*` намеренно совпадают с теми, которые читает сервер
[yandex-tracker-mcp](https://github.com/aikts/yandex-tracker-mcp), так что один
`.env` настраивает и CLI, и MCP-сервер.

### Использование файла .env

Если в каталоге, из которого вы запускаете `yandex`, лежит файл с именем
`.env`, его строки вида `KEY=value` читаются как переменные окружения:

```
TRACKER_TOKEN=y0_...
TRACKER_ORG_ID=123456
```

Здесь легко ошибиться в двух вещах:

- **Файл читается из текущего каталога, а не из проекта, которому
  принадлежит.** Запустите ту же команду каталогом выше — и `.env` не найдётся,
  так что команда поведёт себя иначе: обычно откатится к вашему профилю, иногда
  просто не выполнится. Если команда работает в одной папке и не работает в
  другой, дело почти всегда в этом.
- **Он никогда не перекрывает переменную, уже экспортированную в оболочке.**
  Файл только заполняет пропуски. Набранный ранее в этом окне
  `export TRACKER_TOKEN=...` побеждает `.env`.

Чтобы прочитать файл из другого места, назовите его:

```bash
yandex --env-file ~/secrets/tracker.env config check
```

Добавьте `.env` в `.gitignore`. В нём лежит токен.

## Файлы на диске

Всё, что CLI хранит, лежит в одном каталоге — `~/.yandex-cli`, если
`YANDEX_CLI_HOME` не говорит иначе:

| Файл | Что в нём |
|---|---|
| `~/.yandex-cli/config.json` | Профили и указание, какой из них текущий. Содержит токены. |
| `~/.yandex-cli/session.json` | Текущие очередь и задача, последний результат, история изменений и стек отмены. |
| `~/.yandex-cli/history` | То, что вы набирали в интерактивном режиме, чтобы стрелка вверх работала между запусками. |

Два файла JSON намеренно ведут себя по-разному, когда повреждены:

- **Повреждённый `session.json` — не ошибка.** Сессия нужна для удобства,
  поэтому нечитаемая сессия отбрасывается и CLI начинает с пустой: ни текущей
  задачи, ни истории. Ваши команды продолжают работать.
- **Повреждённый `config.json` — ошибка**, потому что догадки об учётных данных
  были бы хуже остановки. В сообщении назван файл, чтобы вы могли его починить
  или удалить:

```
  ✗ Profile store /Users/you/.yandex-cli/config.json is not valid JSON: Expecting value: line 1 column 1 (char 0)
```

Удалить `session.json` или `history` безопасно: вы теряете текущую задачу, стек
отмены и набранные команды, которые подставляет стрелка вверх, — и больше
ничего. При удалении `config.json` теряются сохранённые профили, и создавать их
придётся заново через `set-profile`.

## Режим только для чтения и другие ограничения

Четыре настройки сужают то, что CLI позволено делать. У каждой есть флаг и
переменная окружения, и каждая отклоняет команду с объяснением, а не молча.

**`--read-only` / `TRACKER_READ_ONLY`** отклоняет любую команду Tracker,
которая что-то меняет: создание задач, их правку, комментирование, переходы по
статусам. Чтения это не касается.

```bash
yandex --read-only tracker issue comment-add TREK-1 --text "hello"
```

```
  ✗ 'issue comment-add' writes to Yandex Tracker, but the CLI is in read-only mode. Unset TRACKER_READ_ONLY or drop --read-only to allow it.
```

**`--wiki-read-only` / `WIKI_READ_ONLY`** делает то же самое для Wiki и
отдельно от Tracker, так что можно разрешить запись в Tracker, оставив страницы
неприкосновенными.

```
  ✗ 'wiki page create' writes to Yandex Wiki, but wiki write access is disabled. Unset WIKI_READ_ONLY or drop --wiki-read-only to allow it.
```

**`--limit-queues` / `TRACKER_LIMIT_QUEUES`** — это список разрешённых ключей
очередей. Очереди вне него недоступны даже для чтения:

```bash
yandex --limit-queues TREK tracker queue get OPS
```

```
  ✗ Queue 'OPS' is not in the allowed list (TREK). Change TRACKER_LIMIT_QUEUES or --limit-queues to widen access.
```

**`--read-only-queues` / `TRACKER_READ_ONLY_QUEUES`** — ограничение поуже:
перечисленные очереди остаются полностью читаемыми, но запись в них
отклоняется. Пригодится, чтобы защитить боевую очередь, оставив остальную
организацию доступной для записи.

```bash
yandex --read-only-queues TREK tracker issue comment-add TREK-1 --text "hello"
```

```
  ✗ 'issue comment-add' writes to queue 'TREK', which is read-only (TRACKER_READ_ONLY_QUEUES=TREK). Drop it from TRACKER_READ_ONLY_QUEUES or --read-only-queues to allow it.
```

Очевидное применение всех четырёх — отдать CLI не себе, а кому-то другому:
скрипту, задаче CI или AI-агенту. Профиль, сохранённый с `--read-only`, или
контейнер с `TRACKER_READ_ONLY=1` в окружении превращают любую разрушительную
команду в отказ.

Это страховка, а не песочница. Окружение стоит выше профиля (см.
[откуда берутся настройки](#откуда-берутся-настройки)), поэтому всё, что может
править окружение или файл настроек, может и снять ограничение. Против
AI-агента надёжный вариант — задать переменную в том окружении, в котором
запускается сам агент, куда ему незачем заглядывать. См.
[AI-агенты](ai-agents.md#как-обезопасить-работу-агента).

## Несколько организаций

Дайте каждой организации свой профиль:

```bash
yandex config set-profile acme --org-id 123456
yandex --profile acme auth add main --services tracker,wiki --token-stdin < /secure/local/oauth-token
yandex config set-profile cloud --cloud-org-id bpf1abc2def3ghi4jkl5 --not-current
yandex --profile cloud auth add main --services tracker,wiki --token-stdin < /secure/local/oauth-token
```

Переключайтесь, когда меняете контекст надолго:

```bash
yandex config use-profile cloud
```

Или загляните в другой профиль ради одной команды, не трогая текущий:

```bash
yandex --profile cloud tracker queue list
```

Помните, что `--profile` старше и окружения, поэтому он поступает правильно
даже в оболочке, где `TRACKER_ORG_ID` экспортирован для чего-то другого.

Если вы вдруг не уверены, в какую организацию только что ушла команда,
`yandex config check` её называет, а строка `backend` показывает ту версию, на
которой работаете вы:

```
  ✓ Connected as John Doe (j.doe)
  backend: yandex-cli 1.0.0
  api_base_url: https://api.tracker.yandex.net
  wiki_base_url: https://api.wiki.yandex.net
  org_id: 123456
  cloud_org_id: -
```

## OAuth и настройки Календаря

Используйте существующее приложение в [Яндекс OAuth](https://oauth.yandex.ru/).
Проверьте его права в настройках (или по адресу
`https://oauth.yandex.ru/client/<client_id>/info`) и включите доступное ему право
Календаря. В настройках одного приложения были выбраны `calendar:all` и отдельные
права чтения/записи Календаря. Существующий OAuth-токен прошёл discovery/create/get
на одном корпоративном аккаунте; минимальные права токена не выделены,
для обычного аккаунта принят тот же клиентский OAuth-путь без отдельной
live-проверки. Обновления встреч используют условную
запись и автоматический scheduling сервера. Целевая live-проверка с отдельным
почтовым ящиком владельца прошла; получение уведомлений подтвердил владелец.
Удаление Яндекса отключено: сервер принял DELETE с устаревшим ETag. См. [текущие ограничения](commands.md#календарь).
Полная совместимость остаётся неподтверждённой.
[Пример OAuth для CalDAV](https://www.yandex.ru/support/yandex-360/business/admin/ru/security-service-applications)
относится к сервисным приложениям и не доказывает совместимость обычного токена.

Получите новый токен через настроенный в вашем приложении
[OAuth-flow](https://www.yandex.ru/dev/id/doc/ru/codes/code-url), используя его
ClientID, зарегистрированный Redirect URI и выданные права Календаря.
Изменение приложения не добавляет права старому токену: пройдите авторизацию
заново и замените токен. CLI принимает уже выданные токены; browser login и
refresh-flow отсутствуют. Не вставляйте токены в чат или аргументы команд.

| Поле профиля | Переменная окружения | По умолчанию |
|---|---|---|
| `oauth_token` | `YANDEX_OAUTH_TOKEN` | не задано |
| `calendar_token` | `CALENDAR_TOKEN` | не задано; приоритет над общим OAuth |
| `calendar_username` | `CALENDAR_USERNAME` | не задано; полный email, например `you@yandex.ru` |
| `calendar_base_url` | `CALENDAR_BASE_URL` | `https://caldav.yandex.ru/` |
| `calendar_timezone` | `CALENDAR_TIMEZONE` | `UTC` |
| `calendar_default` | `CALENDAR_DEFAULT` | не задано; обнаруженный ID календаря |
| `calendar_read_only` | `CALENDAR_READ_ONLY` | `false` |

Поля токенов в таблице относятся к legacy-профилям и окружению. В новых
профилях Календарю назначается именованный OAuth-токен, который может также
обслуживать Трекер/Вики. IAM не поддерживается. Явный --profile исключает
credential-переменные окружения. Сохраните токен через auth:

```bash
yandex config set-profile calendar --calendar-username you@yandex.ru --calendar-timezone Europe/Moscow
yandex --profile calendar auth add main --services calendar --token-stdin < /secure/local/oauth-token
yandex --profile calendar config check --service calendar
```

Stdin не выводится. `config show` полностью скрывает оба новых токена, но
профили хранят их открытым текстом: защищайте локальный config-файл.
После `calendar list` сохраните точный `id` через `--calendar-default ID`.
Корневой `--calendar-read-only`, настройка профиля или `CALENDAR_READ_ONLY=1`
запрещают запись и в REPL. Флаги Tracker/Wiki действуют отдельно.
Проверка календаря выполняет только discovery, не доказывает право записи.
Обычный `config check` по-прежнему проверяет Tracker.

## Именованные токены и назначения сервисов

Каждый профиль независимо хранит свои токены. Сохраните секрет один раз и
назначьте его имя любому сочетанию Трекера, Вики и Календаря. Назначение не
выдаёт OAuth-права; `auth check` проверяет только доступ для чтения.

```bash
yandex --profile work auth setup
yandex --profile work auth status
yandex --profile work auth check
```

Для автоматизации создайте профиль и настройки сервисов, затем передайте секреты
через stdin. Новые команды не принимают секрет аргументом командной строки.

```bash
yandex config set-profile work --org-id 123456
yandex --profile work auth add main --services tracker,wiki --token-stdin < /secure/local/oauth-token
yandex --profile work auth add calendar --services calendar --token-stdin < /secure/local/calendar-token
yandex config set-profile work --calendar-username you@example.com --calendar-timezone Europe/Moscow
yandex --profile work auth check
yandex --profile work auth replace main --token-stdin --check < /secure/local/new-token
yandex --profile work auth assign main --services calendar --check
```

`auth add NAME --create-profile` создаёт явно названный профиль, не делая его
текущим. Без `--services` токен сохраняется неназначенным. Статический IAM задаётся
через `--kind iam --services tracker,wiki`; Календарь IAM не поддерживает.
`all` означает три реализованных сервиса; почта пока недоступна. Перед удалением
назначенного токена через `auth remove NAME` выполните `auth unassign --services
calendar`. `assign` меняет только перечисленные сервисы, а `replace` затрагивает
все сервисы, использующие этот токен.

**Явный `--profile` исключает все credential-переменные окружения, включая
`.env`, даже если сервис в профиле не настроен.** Остальные настройки сохраняют
прежние приоритеты. Без `--profile` токены окружения могут перекрыть текущий
профиль; status показывает фактический источник. Явные credential-флаги остаются
допустимым переопределением. При ошибке другой токен автоматически не пробуется.

Прямые команды по умолчанию работают без сети. `--check` у add/replace/assign
проверяет сохранённый профиль после записи, игнорируя временные credentials.
При сбое проверки код возврата ненулевой, `saved: true`; секрет остаётся сохранён.
Мастер проверяет автоматически. `auth status` работает локально и показывает
последнюю проверку с датой; кешируются только результаты токенов профиля с
привязкой к идентификатору и версии токена. После замены статус not_checked.
Успех проверки не гарантирует права записи. Секреты и фрагменты старых токенов
полностью скрываются.

Существующие legacy-профили продолжают читаться. Перед новыми командами изменения:

```bash
yandex --profile work auth migrate
```

Миграция явная: объединяет одинаковые credentials внутри профиля, сохраняя
назначения. Та же команда восстанавливает смешанный формат, не меняя новых
назначений. Подозрительные значения переносятся с предупреждением о замене.
Новые профили используют auth v1; старые credential-setters работают только на
существующих legacy-профилях. Старые CLI игнорируют auth v1 и могут подхватить
окружение: обновите все установки до миграции. После изменения токенов
перезапустите работающий MCP; REPL перечитывает настройки между командами.
Секреты остаются в локальном JSON с доступом только владельца, где это поддерживается.

## Изменения совместимости

Новые профили хранят токены через `auth`, независимо друг от друга. Старые профили читаются до явного `auth migrate`; старые версии CLI не смогут использовать перенесённые токены. Явный `--profile` игнорирует токены из переменных окружения и `.env`. Флаги токенов сохраняют приоритет над выбранным профилем. Значения токенов полностью скрыты в диагностике. HTTP 401/403 не вызывает переключения на другой токен.
