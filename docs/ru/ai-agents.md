# Использование CLI из AI-агента

Агенты для программирования — Claude Code, Cursor, Codex, GitHub Copilot,
Gemini CLI — умеют выполнять команды в терминале. Значит, `yandex` можно
передать одному из них: «закрой задачи, которые я починил на этой неделе»,
«запиши итоги встречи на командной странице вики», «какие из моих задач не
двигались уже месяц».

Загвоздка в том, что агент никогда не читал эту документацию. Если оставить его
гадать, он выдумает несуществующие опции и сдастся. Поэтому CLI носит с собой
собственное руководство, написанное для агента, а не для вас, и устанавливает
его туда, где агент его найдёт.

## Что такое skill-файл для агента

Это один файл Markdown, `SKILL.md`, который лежит **внутри** бинарника
`yandex`. Ничего не нужно скачивать и нечего вручную поддерживать в
актуальном состоянии.

В нём описаны все группы команд, язык запросов Tracker, контракт `--json`,
последовательности «сначала выясни, потом пиши» (спросить у очереди её
обязательные поля, прежде чем создавать в ней задачу; спросить у задачи её
переходы, прежде чем её двигать), какие операции умеет откатывать
`session undo` и какие бывают отказы вместе с лекарством от каждого. Грубо
говоря — все [команды](commands.md), сжатые в ту форму, которую агент читает
лучше всего: таблица команд и список разобранных примеров, без объяснений, что
такое очередь.

Агенты, умеющие работать со skill-файлами, читают такие файлы автоматически и
обращаются к ним, когда задача выглядит подходящей. Срабатывает это благодаря
описанию в начале файла: там по именам названы Tracker и Wiki, так что запрос,
где упомянут любой из них, подтягивает файл.

## Установка

```bash
yandex skill install
```

Эта команда копирует `SKILL.md` из бинарника в `.agents/skills/yandex/` —
каталог, общий для агентов, — и связывает собственный каталог каждого агента
символической ссылкой на него. В терминале она сначала задаёт два вопроса,
разобранных ниже; как только вы ответите, она печатает, что записала:

```
Installed the yandex skill to /Users/you/work/.agents/skills/yandex/SKILL.md
Linked /Users/you/work/.claude/skills/yandex -> ../../.agents/skills/yandex
```

Файл один, поэтому его обновление доходит сразу до всех агентов. Ссылки
относительные, так что перенос или копирование проекта их не ломает.

Запускайте её из того каталога проекта, в котором агенту нужен доступ к
Tracker. Существующая установка заменяется, так что повторный запуск всегда
безопасен.

### Ответы на вопросы

Без флагов `skill install` задаёт два вопроса.

**Каким агентам отдать skill-файл?** Отметить можно сразу несколько:

```
? Which agents should get the skill?
  Space to select · a all · Enter confirm

❯ ◯ claude-code
  ◯ codex
  ◯ copilot
  ◯ cursor
  ◯ gemini
  ◯ universal
```

Стрелки `↑` и `↓` двигают указатель `❯`, `Space` отмечает агента, на котором
указатель стоит, `a` отмечает всех сразу (повторное нажатие снимает отметки), а
`Enter` подтверждает. Подтверждение без единой отметки ничего не делает, а лишь
спрашивает снова — выберите хотя бы одного.

**Куда его положить?** Один из двух вариантов, выбирается стрелками и `Enter`:

```
? Where should it go?
  ↑↓ to move · Enter confirm

❯ ● This directory only
  ○ The whole user account
```

*This directory only* кладёт skill-файл в тот проект, в котором вы стоите, так
что он действует для этого репозитория и ни для какого другого. *The whole user
account* кладёт его в домашний каталог, где его видят все проекты. Начните с
каталога; расширите позже, если заметите, что ставите его снова и снова.

Когда команду запускают из скрипта или через конвейер, а не в терминале,
рисовать список выбора негде, поэтому те же два вопроса задаются обычным
текстом:

```
Which agents should get the skill?
  1. claude-code
  2. codex
  3. copilot
  4. cursor
  5. gemini
  6. universal
Numbers, comma separated [6]:
Install for the whole user account? (no = only this directory) [y/N]:
```

### Как пропустить вопросы

`-a` называет агента (повторите для нескольких), `-g` означает весь
пользовательский аккаунт, `--project` — этот каталог, а `-y` принимает значения
по умолчанию для всего, о чём не спросили:

```bash
yandex skill install -a claude-code -g -y      # этот пользователь, Claude Code
yandex skill install -a cursor -a codex -y     # этот каталог, два агента
yandex skill install -y                        # этот каталог, `universal`
yandex skill install --dir ./somewhere/yandex  # явно указанный каталог
```

`--dir` вообще обходит раскладку каталогов агентов и пишет в названный вами
каталог — для инструмента, который хранит свои skill-файлы там, куда ни один
из встроенных вариантов не попадает.

## Поддерживаемые агенты

| Агент | В проекте | Для пользовательского аккаунта |
|---|---|---|
| `claude-code` | `.claude/skills/yandex/` | `~/.claude/skills/yandex/` |
| `cursor` | `.agents/skills/yandex/` | `~/.cursor/skills/yandex/` |
| `codex` | `.agents/skills/yandex/` | `~/.codex/skills/yandex/` |
| `copilot` | `.agents/skills/yandex/` | `~/.copilot/skills/yandex/` |
| `gemini` | `.agents/skills/yandex/` | `~/.gemini/skills/yandex/` |
| `universal` | `.agents/skills/yandex/` | `~/.config/agents/skills/yandex/` |

**Сам файл всегда попадает в строку `universal`** — `.agents/skills/yandex/` в
проекте и `~/.config/agents/skills/yandex/` для пользовательского аккаунта. Все
остальные каталоги в таблице — символические ссылки на него, и создаются они
только для тех агентов, которых вы назвали.

Каталог `.agents/skills/` — общепринятое соглашение, поэтому в проекте он и так
покрывает сразу Cursor, Codex, Copilot и Gemini; вот почему при перечислении
нескольких из них пишется один файл, ссылки не создаются и печатается одна
строка:

```bash
yandex skill install -a cursor -a codex -y
```

```
Installed the yandex skill to /Users/you/work/.agents/skills/yandex/SKILL.md
```

`universal` — тот же самый каталог под именем, которое ничего не обещает
насчёт того, какой агент его читает. Это вариант по умолчанию, когда вы
проходите вопросы клавишей `Enter`, и то, что выбирает один только `-y`.

## Любой другой агент

Любому инструменту, который принимает инструкции текстом, можно отдать
skill-файл в том формате, который ему нужен. Напечатайте его:

```bash
yandex skill show
```

Перенаправьте вывод в тот файл, который читает ваш инструмент:

```bash
yandex skill show > AGENTS.md
```

Или найдите файл на диске, чтобы скопировать его, сделать на него ссылку или
вставить из него текст:

```bash
yandex skill path
```

Команда печатает один абсолютный путь внутрь установленного комплекта. Читайте
его, но не правьте: следующее обновление устанавливается в свой собственный
каталог, и сделанная там правка останется со старой версией.

## Без CLI

Тот же самый `SKILL.md` опубликован и отдельно — как
[`skills/yandex/SKILL.md`](https://github.com/AntonLisovoy/yandex-cli/blob/main/skills/yandex/SKILL.md)
в публичном репозитории. Агенту можно отдать skill-файл ещё до установки CLI —
или на машине, где CLI не появится никогда:

```bash
npx skills add AntonLisovoy/yandex-cli
```

Это [skills CLI](https://skills.sh/docs/cli). Он кладёт файл в текущий проект
или, с флагом `-g`, в ваш домашний каталог. Прочитать файл, ничего не
устанавливая:

```bash
npx skills use AntonLisovoy/yandex-cli@yandex
```

Опубликованную копию обновляет тот же самый шаг, который публикует эту
документацию, поэтому она описывает свежайший релиз — не обязательно ту версию,
которая стоит у вас. Когда они расходятся, правду про ваш бинарник говорит
`yandex skill install`.

## После обновления

Ссылки идут между вашими собственными каталогами; **внутрь установленного
бинарника не ссылается ничто**. `skill install` копирует файл оттуда, поэтому
копия в вашем проекте описывает ту версию CLI, которая была установлена в день
запуска команды, и будет описывать её вечно.

Так сделано намеренно. Каждый выпуск распаковывается в свой каталог, так что
ссылка внутрь бинарника после обновления по-прежнему бы разрешалась — и молча
продолжала бы отдавать старый skill-файл, а это отказ хуже, чем устаревшая
копия, которую видно.

Поэтому после каждого обновления CLI запускайте установку заново:

```bash
yandex skill install -y
```

Ничего не сломается, если вы забудете: агент будет работать по чуть более
старому списку команд. Но о команде, добавленной в новой версии, агент не будет
знать.

## Когда ссылки недоступны

Некоторые файловые системы отказываются создавать символические ссылки, а
Windows разрешает их только при включённом Developer Mode. Когда ссылку создать
не удалось — или когда в каталоге агента уже лежат не наши файлы — установка
кладёт туда копию `SKILL.md` и сообщает об этом:

```
Could not link it: ... That directory now holds a copy, so run the install
again after upgrading the CLI.
```

Всё работает; разница лишь в том, что такой каталог хранит собственную копию,
поэтому после каждого обновления установку придётся запускать заново.

Ничего из того, что положили туда не мы, установка не удаляет. Она удаляет ровно
один файл — тот `SKILL.md`, который записала предыдущая установка, — и только
после этого пустой каталог. Обычный файл, стоящий там, где должен быть каталог
скила, остаётся на месте, а установка называет его и идёт дальше:

```
Left /Users/you/work/.claude/skills/yandex alone: it is a file, not a
directory. Move it aside and install again.
```

## MCP-сервер

`yandex mcp` отдает Tracker и Wiki агенту по Model Context Protocol (stdio).
Подходит, когда у агента нет шелла или нужны типизированные инструменты вместо команд.
Skill и MCP-сервер можно использовать вместе.

Сервер читает тот же конфиг, что и остальные команды. Флаги ставятся **до** `mcp`:

```json
{
  "mcpServers": {
    "yandex": {
      "command": "yandex",
      "args": ["--profile", "agent", "--read-only", "mcp"]
    }
  }
}
```

- **Claude Code:** `claude mcp add yandex -- yandex --profile agent mcp`
- **Claude Desktop, Cursor:** JSON выше в настройках MCP приложения. Десктопные
  приложения не видят `PATH` вашего шелла, поэтому укажите полный путь к бинарнику,
  например `/opt/homebrew/bin/yandex` (узнать: `which yandex`).
- **Codex:** в `~/.codex/config.toml`:

  ```toml
  [mcp_servers.yandex]
  command = "yandex"
  args = ["--profile", "agent", "mcp"]
  ```

`.env` резолвится от рабочего каталога *MCP-клиента*, а не вашего проекта - cwd,
в котором стартует сервер, выбирает клиент, а у десктопного приложения это редко
папка проекта. Держите креды в профиле (`--profile`) или в собственной карте `env`
клиента, а не в проектном `.env`.

### Read-only и ограниченные режимы

- `--read-only` убирает из списка инструменты записи в Tracker, `--wiki-read-only`
  в Wiki: агент их не видит.
- `--read-only-queues` оставляет инструменты записи, но запись в перечисленную очередь
  завершится ошибкой.
- `--limit-queues` сужает поиск, подсчет, список очередей, связи и обращения по ключу
  до перечисленных очередей. Это защита от ошибок, а не граница безопасности: поля
  разрешенной задачи (родитель, история) могут упоминать задачи из других очередей, а
  доски, спринты, проекты и пользователи не фильтруются. Настоящая граница это права
  токена.

## Как обезопасить работу агента

У агента, управляющего `yandex`, ровно тот доступ, что и у вашего токена. Он
может закрывать задачи, удалять страницы вики и переписывать права очереди — не
потому, что хочет, а потому, что неверно понял просьбу. Две из этих вещей
`yandex session undo` откатить не умеет.

Лекарство — дать агенту более узкий CLI, чем тот, которым пользуетесь вы:

- **`--read-only` / `TRACKER_READ_ONLY`** отклоняет любую запись в Tracker, так
  что агент, который подводит итоги, отчитывается или ищет, ничего не теряет.
- **`--wiki-read-only` / `WIKI_READ_ONLY`** делает то же самое для Wiki и
  отдельно, так что агент может заводить задачи, не трогая ваши страницы.
- **`--limit-queues` / `TRACKER_LIMIT_QUEUES`** прячет все очереди, кроме
  названных, так что агент, посланный за делами одной команды, не забредёт к
  другой.
- **`--read-only-queues` / `TRACKER_READ_ONLY_QUEUES`** оставляет названные
  очереди читаемыми, но запись в них отклоняет, так что агент может изучить
  боевую очередь, ничего в ней не меняя.

Сохраните профиль только для чтения и отдайте его агенту:

```bash
yandex config set-profile agent --token y0_exampletokenvalue --org-id 123456 --read-only --limit-queues TREK --not-current
```

`--not-current` оставляет вашу собственную работу на вашем собственном профиле.
Три настройки из четырёх могут жить в таком профиле; **`--read-only-queues` —
нет**: у `set-profile` для неё нет опции, так что она может прийти только из
флага или из `TRACKER_READ_ONLY_QUEUES` в окружении агента. Дальше агент
выполняет каждую команду через ограниченный профиль:

```bash
yandex --profile agent tracker issue find -q "Queue: TREK AND Updated: week()"
```

и запись отклоняется — сообщением, которое точно говорит, что её остановило:

```
  ✗ 'issue comment-add' writes to Yandex Tracker, but the CLI is in read-only mode. Unset TRACKER_READ_ONLY or drop --read-only to allow it.
```

**Профиль — это страховка, а не песочница.** Агент, который может выполнить
`yandex config set-profile`, может и снять ограничение, а тот, кто может
править вашу оболочку, может убрать `--profile agent`. Когда ограничение должно
держаться по-настоящему, задавайте его в том окружении, в котором запускается
сам агент: `TRACKER_READ_ONLY=1` в собственном окружении агента или контейнер,
запущенный с этой переменной, — куда агенту незачем заглядывать и где нет
команды, которая изменила бы её изнутри.

Все четыре настройки разобраны целиком, с сообщением, которое выдаёт каждая, в
[настройке](configuration.md#режим-только-для-чтения-и-другие-ограничения).
