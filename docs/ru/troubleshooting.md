# Решение проблем

Каждое сообщение ниже — то, которое CLI действительно печатает. Найдите своё, и
строка или абзац рядом скажут, что оно значит и что делать.

Ошибки самого CLI начинаются с красного `✗`. Ошибки от Яндекса завёрнуты в
собственную строку CLI, где назван HTTP-статус. Ошибки о *форме* вашей командной
строки — опечатка в опции, значение не в том виде — приходят от разборщика
аргументов и начинаются с `Error:`.

## Команда не найдена

```
command not found: yandex
```

Ваша командная оболочка — программа, читающая то, что вы набираете, — ищет
команды только в папках из списка, который она хранит; этот список называется
PATH. Это сообщение означает, что `yandex` не лежит ни в одной из них. Причин
тому две.

**Вероятная: `~/.local/bin` не входит в ваш PATH.** Установщик кладёт `yandex`
именно туда, а на многих системах этой папки в списке нет. Установщик это
замечает и говорит об этом в конце:

```
Note: /Users/you/.local/bin is not on your PATH. Add it:
  export PATH="/Users/you/.local/bin:$PATH"
```

Выполнение этой строки с `export` чинит то окно терминала, в котором вы сейчас,
и только его. Чтобы починить навсегда, впишите эту строку в файл, который ваша
оболочка читает при каждом запуске.

Для **zsh**, который используется по умолчанию в macOS:

```bash
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc
```

Для **bash**, который используется по умолчанию в большинстве дистрибутивов
Linux:

```bash
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
```

В macOS с bash пишите в `~/.bash_profile` вместо `~/.bashrc`. Если вы не
уверены, какая у вас оболочка, это скажет `echo $SHELL`.

Затем откройте новое окно терминала — файл читается при запуске, так что уже
открытое окно его не подхватит — и снова попробуйте `yandex --version`.

**Вторая: установка не завершилась.** Проверьте, есть ли файл вообще:

```bash
ls -l ~/.local/bin/yandex
```

Если он есть, вы получите одну строку с его описанием, и тогда дело в PATH.
Если ничего не установилось, `ls` сообщит, что файла нет; точная формулировка в
macOS и Linux отличается, но всегда заканчивается на `No such file or
directory`. В macOS:

```
ls: /Users/you/.local/bin/yandex: No such file or directory
```

Запустите установщик снова и прочитайте, что он напечатает. Неудавшаяся
загрузка, несовпавшая контрольная сумма или папка, в которую не удалось
записать, — всё это останавливает его с соответствующим сообщением. Инструкции
по установке — в [начале работы](getting-started.md#2-установка).

## Учётные данные и организация

Эти сообщения приходят от собственных проверок CLI, до того как что-либо
уходит в Яндекс. У всех них под `--json` стоит `"type": "ConfigError"`.

| Сообщение | Что оно значит | Что делать |
|---|---|---|
| `No Yandex Tracker credentials found.` | Токена нет вообще: ни в командной строке, ни в окружении, ни в текущем профиле. | Сохраните профиль командой `yandex config set-profile work --token y0_... --org-id ...` или экспортируйте `TRACKER_TOKEN`. Само сообщение перечисляет все три способа. |
| `Both org_id and cloud_org_id are set — the API accepts exactly one.` | Заданы оба идентификатора организации, а Яндекс принимает либо тот, либо другой. Обычно это профиль, сохранённый дважды: по разу с каждым. | Уберите один. Если он в профиле — `yandex config delete-profile work` и сохранить заново только с нужным идентификатором. |
| `No organization id found.` | Токен есть, но ничто не говорит, о какой организации спрашивать. | Задайте `TRACKER_ORG_ID` (Yandex 360 или локальная установка) **или** `TRACKER_CLOUD_ORG_ID` (Yandex Cloud) — см. [начало работы](getting-started.md#5-найдите-идентификатор-организации). |
| `Profile 'agent' not found in /Users/you/.yandex-cli/config.json. Known profiles: cloud, work` | Вы запросили профиль по имени, а такого профиля нет. Сообщение перечисляет те, что есть. | Сверьте написание с этим списком или создайте профиль. Когда профилей нет вовсе, в списке стоит `<none>`. |

Первое из них печатает способы исправления целиком:

```
  ✗ No Yandex Tracker credentials found.
      Set one of:
        export TRACKER_TOKEN=<OAuth token>       # https://yandex.ru/support/tracker/ru/concepts/access
        export TRACKER_IAM_TOKEN=<IAM token>     # Yandex Cloud
      or pass --token / --iam-token, or save a profile:
        yandex config set-profile default --token ... --org-id ...
```

`yandex config show` показывает, что CLI считает своими настройками после того,
как применены все четыре слоя, и это обычно самый быстрый способ понять, какой
из них не тот. Слои объясняет
[настройка](configuration.md#откуда-берутся-настройки).

## Ошибки от API Яндекса

Эти ошибки приходят от самого Яндекса. CLI добавляет статус, сохраняет всё,
что API сказал о причине, и дописывает, что с этим делать. Под `--json` у всех
них стоит `"type": "BackendError"`, а код возврата равен 1.

| Статус | Сообщение | Что делать |
|---|---|---|
| 401, 403 | `Yandex rejected the credentials (HTTP 401)` | Токен не тот, просрочен или принадлежит пользователю без доступа к этой организации. См. примечание ниже. |
| 404 | `Not found (HTTP 404): <url>` или `Issue 'TREK-9' not found, or the token has no access to it.` | Ключа не существует — либо он существует, но ваш токен его не видит. Снаружи эти два случая намеренно неразличимы. Сначала проверьте написание, потом — открывается ли задача в браузере. |
| 409 | `Conflict (HTTP 409)` плюс `The entity changed since you read it. Re-read it to get the current version/revision and retry.` | Кто-то отредактировал задачу, страницу или таблицу между вашим чтением и вашей записью. Прочитайте заново и повторите запись поверх новой версии. |
| 422 | `The API rejected the payload (HTTP 422)` плюс `Check required fields with 'yandex tracker queue fields <QUEUE>'.` | Что-то в отправленном неприемлемо: чаще всего это поле, которого требует очередь, а вы его не заполнили, или значение не в том виде. API называет поле, к которому придрался; CLI сохраняет этот текст. |
| 429 | `Rate limited by Yandex (HTTP 429)` плюс `Retry with a lower page size or after a pause.` | Слишком много запросов слишком быстро. Уменьшите `--per-page`, уберите `--all` или подождите и попробуйте снова. |
| - | `Cannot reach <address>: <reason>. Check the network, a proxy, or --api-base-url.` | По этому адресу никто не ответил. Проверьте, что вы в сети, что корпоративный прокси не мешает и что `--api-base-url` не указывает куда-то не туда. |
| - | `Request timed out after 30.0s. Increase it with --timeout or TRACKER_TIMEOUT.` | Яндекс ответил слишком медленно — или запрос действительно большой. Поднимите ограничение через `--timeout 60` либо задайте `TRACKER_TIMEOUT`. |

**Про 401 и 403: последняя строка называет заголовок организации, который был
отправлен на самом деле.**

```
  ✗ Yandex rejected the credentials (HTTP 401): Unauthorized
      Check TRACKER_TOKEN / TRACKER_IAM_TOKEN and that the token's user has access to this organization.
      Organization header in use: X-Org-ID=123456
```

`X-Org-ID` означает, что CLI взял `TRACKER_ORG_ID`; `X-Cloud-Org-ID` — что он
взял `TRACKER_CLOUD_ORG_ID`. Эта единственная строка — самый быстрый способ
заметить самую частую причину отказа, а она вовсе не в плохом токене, а в
*другом* виде идентификатора организации: организация из Yandex Cloud, о
которой спросили через `--org-id`, отвергается ровно так же, как неверный
пароль. Если названный заголовок не тот, который использует ваша организация, —
вот и ответ: поменяйте и попробуйте снова.

## Ограничения доступа, которые накладывает сам CLI

**Эти ошибки идут от того, как настроено у вас, а не от Яндекса.** CLI
отказывает команде до того, как что-либо отправит. Это важно, потому что
формулировка читается как проблема с правами на сервере, и люди идут искать в
административных страницах Tracker настройку, которой там нет. С вашей учётной
записью всё в порядке: то, что сужает разрешённое CLI, находится локально — это
флаг, переменная окружения или сохранённый вами профиль.

`yandex config show` перечисляет ограничения, действующие прямо сейчас.

**Очередь вне списка разрешённых** (`AccessDenied`):

```
  ✗ Queue 'OPS' is not in the allowed list (TREK). Change TRACKER_LIMIT_QUEUES or --limit-queues to widen access.
```

Задан `TRACKER_LIMIT_QUEUES` или `--limit-queues`, то есть список разрешённых
очередей, а запрошенной в нём нет. Очереди вне списка недоступны и для чтения,
так что это сообщение появляется не только на записи, но и на чтении.

**Ключ, который не является ключом задачи** (`AccessDenied`, хотя на самом деле
это опечатка):

```
  ✗ 'TREK' is not an issue key. Expected the form QUEUE-123.
```

Ключ задачи — это очередь, дефис и число. `TREK` сам по себе — очередь, и он
относится к `yandex tracker queue get`, а не к `yandex tracker issue get`.

**Режим только для чтения** (`ReadOnlyError`):

```
  ✗ 'issue create' writes to Yandex Tracker, but the CLI is in read-only mode. Unset TRACKER_READ_ONLY or drop --read-only to allow it.
```

У Wiki свой собственный переключатель, и отказывает он отдельно:

```
  ✗ 'wiki page create' writes to Yandex Wiki, but wiki write access is disabled. Unset WIKI_READ_ONLY or drop --wiki-read-only to allow it.
```

**Очередь, закрытая на запись** (`ReadOnlyError`), пока остальные остаются
доступными для записи:

```
  ✗ 'issue comment-add' writes to queue 'TREK', which is read-only (TRACKER_READ_ONLY_QUEUES=TREK). Drop it from TRACKER_READ_ONLY_QUEUES or --read-only-queues to allow it.
```

Все четыре настройки описаны в
[настройке](configuration.md#режим-только-для-чтения-и-другие-ограничения).
Помните, что ограничение может прийти из сохранённого профиля с тем же успехом,
что и из флага или переменной окружения: `yandex config show` печатает
действующее значение, что бы из трёх его ни задало.

## Сессия и аргументы

**В сессии нет задачи.** Команде, которой нужна задача, её не дали, а
запомненной нет:

```
  ✗ No issue given and no current issue in the session. Pass an issue key or run: session use-issue QUEUE-1
```

Передайте ключ или задайте его один раз командой
`yandex session use-issue TREK-42`. Вариант про очередь читается так же:

```
  ✗ No queue given and no current queue in the session. Pass a queue key or run: session use-queue QUEUE
```

**Отменять нечего.** Стек отмены пуст:

```
  ✗ Nothing to undo.
```

Либо ничего обратимого ещё не делали, либо последним изменением было одно из
тех, которые откатить нельзя: переход, перенос или удаление. Они всё равно
записаны: `yandex session history` показывает их со значением `no` в колонке
`UNDOABLE`. Полный список обратимого — в
[командах](commands.md#отмена-undo).

**`--field` не в форме `key=value`.** Это сообщение приходит от разборщика
аргументов, поэтому в нём стоит `Error:`, а не `✗`:

```
Error: Invalid value: 'bad' is not in key=value form (e.g. --field storyPoints=3)
```

Каждый `--field` принимает одну пару `key=value` без пробелов вокруг `=`. Для
второго поля повторите опцию: `--field storyPoints=3 --field team=platform`.

**Неверный JSON.** Опции, принимающие JSON, — `--rows`, `--columns`,
`--permissions`, `--actions` и им подобные — сообщают, где разборщик сдался:

```
Error: Invalid value: --rows is not valid JSON: Expecting value: line 1 column 3 (char 2)
```

Обычные причины — одинарные кавычки там, где JSON требует двойные, лишняя
запятая в конце или оболочка, съевшая ваши кавычки. Заключите всё значение в
одинарные кавычки, чтобы оболочка его не трогала, а внутри используйте двойные:

```bash
yandex wiki grid add-rows g-1 --rows '[{"task": "Ship v1", "owner": "j.doe"}]'
```

Те же опции принимают `@file`, чтобы прочитать данные из файла, — так удобнее
для всего длинного. Когда файл прочитать не удаётся, сообщение его называет:

```
Error: Invalid value: Cannot read --rows from rows.json: [Errno 2] No such file or directory: 'rows.json'
```

Это проблема с путём, а не с JSON: путь отсчитывается от каталога, в котором вы
стоите.

## Экспорт

Экспорт отказывается заменять уже существующий файл:

```
  ✗ report.csv already exists. Pass --overwrite to replace it.
```

Так сделано намеренно, чтобы повторный запуск не уничтожил молча тот отчёт,
который вы собирались отправить. Добавьте `--overwrite`, если заменить его — это
и есть то, чего вы хотели, или пишите под новым именем:

```bash
yandex export issues -q "Queue: TREK AND Updated: week()" -o report.csv --format csv --overwrite
```

## macOS: «не удалось проверить разработчика»

**Это касается только тех, кто скачал архив со страницы Releases в браузере.**
Браузеры помечают каждую загрузку признаком `com.apple.quarantine`, а macOS
отказывается запускать помещённую в карантин программу от неопознанного
разработчика (в англоязычной системе сообщение звучит как «cannot be opened
because the developer cannot be verified»). `curl` и Homebrew этот признак не
ставят, так что если вы устанавливали однострочным установщиком или через
`brew install`, проблема не ваша и дальше можно не читать.

Если вы всё же скачали архив в браузере, снимите признак с того, что
распаковали. В архиве лежит папка, названная по версии и типу машины —
например, `yandex-cli-1.0.0-macos-arm64`, — а в ней `yandex` и библиотеки,
которые он загружает, поэтому снимайте признак со всей папки, а не с одного
файла:

```bash
xattr -dr com.apple.quarantine ~/Downloads/yandex-cli-1.0.0-macos-arm64
```

Подставьте ту папку, которую распаковали на самом деле. Затем запустите
`yandex` снова.

Более простой способ, которому и стоит отдать предпочтение, — установить
обычным путём: тогда признак не появляется вовсе:

```bash
curl -LsSf https://raw.githubusercontent.com/AntonLisovoy/yandex-cli/main/install.sh | sh
```

## Обновление

Через Homebrew:

```bash
brew upgrade yandex-cli
```

Иначе выполните ту же однострочную команду установщика ещё раз. Он забирает
текущий выпуск, распаковывает его рядом со старым и перенаправляет на него
`~/.local/bin/yandex`:

```bash
curl -LsSf https://raw.githubusercontent.com/AntonLisovoy/yandex-cli/main/install.sh | sh
```

**Ваши настройки сохраняются.** Ни тот, ни другой способ не трогает
`~/.yandex-cli`: профили, текущая задача, история и стек отмены остаются на
месте. Проверьте это через `yandex --version`, а затем `yandex config check`.

**Skill-файл для агента сам себя не обновляет.** `yandex skill install`
копирует файл, а не ссылается на него, поэтому копия в вашем проекте всё ещё
описывает ту версию, которая была у вас в момент запуска. Запустите установку
заново после обновления:

```bash
yandex skill install -y
```

Почему это устроено именно так и что теряется, если забыть, — в
[AI-агентах](ai-agents.md#после-обновления).

## Удаление

Через Homebrew:

```bash
brew uninstall yandex-cli
```

Иначе удалите программу и ссылку на неё:

```bash
rm -rf ~/.local/share/yandex-cli ~/.local/bin/yandex
```

В обоих случаях **ваши настройки намеренно остаются на месте**, чтобы повторная
установка вернула вас туда, где вы были. Чтобы удалить и их:

```bash
rm -rf ~/.yandex-cli
```

В этом каталоге лежит `config.json`, а в `config.json` — ваш OAuth-токен
открытым текстом. Удалить его — правильный поступок на машине, которую вы
кому-то передаёте, а сам токен стоит отозвать на <https://oauth.yandex.ru>, если
его мог увидеть кто-то ещё.

## Если ничего не помогло

Начните с этого:

```bash
yandex config show
```

**Токен выводится замаскированным** — только первые и последние четыре символа
и длина. А вот строки `config_file` и `session_file` не маскируются и содержат
ваше имя пользователя, так что перед отправкой обрежьте эти две; остальное
публиковать безопасно.

Затем заведите задачу на
<https://github.com/AntonLisovoy/yandex-cli/issues>, приложив три вещи:

1. Тот самый вывод `yandex config show`.
2. Точную команду, которую вы выполнили.
3. Точное сообщение, которое получили в ответ, — скопированное, а не
   пересказанное.

Добавьте `yandex --version`, если сообщаете об изменившемся поведении. С этим
проблема обычно воспроизводится с первого раза.
